One lab computer. One controlled run path.

Two people use the dashboard or CLI. The same engine controls tools, records results, and requests assistance from approved models.

Solid arrows show commands or data. The dashed model path is optional assistance. Model access routes requests to local or approved external providers. The overview omits network equipment.

Host or gateway firewall rules must restrict runner traffic to approved destinations. The runner receives no host folders, personal credentials, or host management access.

Model access · proposed

One access module. Two model destinations.

The engine uses a small model access module on the lab host. It selects an approved model and checks the campaign data policy.

Local-only campaign

Use open-weight models on the lab computer. Deny external model calls. Never switch to a cloud model after a local failure.

Approved external campaign

Select a provider, exact model ID, and allowed data before starting the campaign. Send only approved excerpts. Exclude credentials and session tokens.

Comparison campaign

Give local and external models the same approved test cases. Compare detection, false positives, latency, cost, and reviewer effort.

Start with one inference service.

For two operators, run the open-weight model on the lab computer initially. Keep inference under a separate service account from the runner.

Limit model memory and concurrent requests. Measure response time and runner performance during calibration. Load only models that fit the available hardware.

Stage 1 · One computer

The runner VM and inference service share hardware. Process accounts separate access, but GPU, memory, power, and failures remain shared.

Stage 2 · Dedicated GPU host

Move inference when memory pressure, latency, or isolation needs justify it. Replace loopback access with a private authenticated endpoint.

Stage 3 · Cluster

Add multiple inference hosts only when model size or concurrent demand requires them. Account for interconnect, scheduling, upgrades, and failure handling.

A separate GPU host is not a cluster. Only the model access service can reach its inference endpoint. Runner tools continue through the controlled relay.

Keep the module small.

Start with one local runtime adapter and one external API adapter inside the existing host service. A separate gateway server is unnecessary initially.

Store provider keys under the host service account. The runner VM receives no provider keys. Tools that need models use a bounded relay.

The relay authenticates the run and tool step. It applies the same model, data, time, and cost limits. Tools cannot choose arbitrary providers.

Models suggest test cases and explain evidence. The run engine checks scope and dispatches tools. Model output cannot authorize new targets or commands.

Model registry and acceptance checks
  • Record each local model's source, license, weight hash, quantization, runtime version, and memory needs.
  • Record each external provider's model ID, endpoint, account access, retention terms, and approved data class.
  • Check tool calling, structured output, and context limits for each adapter. An API format match does not establish tool compatibility.
  • Run seeded tests before accepting a model for planning, investigation, or review. Cyber branding does not establish reliable findings.
  • Test that local-only campaigns block cloud calls. Test that tool steps cannot read keys or change providers.
  • Record provider, model version, prompt version, usage, and evidence references for each call. Redact secrets in saved records.

Grok 3.7 Cyber is the specialist external endpoint identified by the operator. Its exact API URL, model ID, access, and data terms remain pending confirmation. Public xAI documentation does not establish this specific endpoint. Use the provider contract to configure its adapter.

External target

The WAF protects a large corporate website.

Start with an approved hostname and a small set of routes. Add routes in stages after the first campaign passes its checks.

Public pages

Test approved page paths and query inputs. Include normal requests to check false positives.

APIs and sign-in

Use approved API routes and test accounts. Authentication support needs a separate adapter before these tests can run.

Backend services

The website can use many backend services. A public URL does not approve direct access to those services.

Record the hostname, route, method, input, session role, and expected result for each case. Use one request budget across all tools.

Coordinate the test window with the site owner. Correlate request IDs with WAF logs and application logs. Exclude third-party services unless approved.

The current collector supports unauthenticated GET requests with query inputs. Corporate authentication, POST bodies, and API workflows remain proposed additions.

Follow one campaign from either interface.

These controls explain the design. They do not start tools or send requests.

Account for every tool. Measure test coverage.

All supplied repositories stay in the inventory. The engine runs applicable, calibrated adapters and preserves their original artifacts.

Additional tools and coverage limits

The registry also lists Nuclei, Nmap, ProjectDiscovery httpx, subfinder, Semgrep, CodeQL, Claude Code, curl, DNS utilities, and jq.

Source checks need source access. Origin research needs approved assets. PyRIT needs an AI target. Agent provider compatibility needs testing.

An outer CLI wrapper cannot control every internal agent request. An adapter must enforce scope and limits or remain blocked.

Keep execution authority outside model output.

This design proposes controls that need acceptance tests. Separate accounts on one computer do not provide independent, tamper-proof evidence.

Minimal security checklist
  1. Keep the dashboard private.
  2. Use two named operator accounts.
  3. Keep the model API on loopback.
  4. Disable cloud model routes for local-only campaigns.
  5. Restrict runner egress independently of tool instructions.
  6. Keep secrets out of browser responses and exports.
  7. Back up configuration and evidence separately.
  8. Check VM reset, stop behavior, and backup recovery.

Build the smallest useful workflow first.

Acceptance: start a scoped run in the UI, inspect it in the CLI, stop it through either interface, and recover the same evidence.
